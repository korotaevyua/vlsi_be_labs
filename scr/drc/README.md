# Проверка GDS в Magic

Вариант задания для лабораторной работы: [«Проверка топологии DRC»](../../docs/drc.md).

Проверка выполняется отдельным этапом после генерации GDS. Ее входные данные — записанный GDS файл, имя верхнего блока и технологический файл с правилами SKY130. Результат — текстовый отчет с описаниями нарушений и координатами в микрометрах.

## Последовательность запуска

1. Выполните генерацию `seven_segment_seconds.gds` по разделу [«Генерация GDS»](../../docs/gds.md). Завершите сеанс Magic, в котором создавался GDS, командой:

```tcl
quit -noprompt
```

2. Из папки `work/gds` откройте полученный файл в KLayout:

```bash
klayout seven_segment_seconds.gds
```

Просмотрите топологию блока и закройте KLayout.

3. В том же терминале создайте отдельную рабочую папку для DRC:

```bash
mkdir -p ../drc && cd ../drc
```

4. Откройте `scr/drc/drc.tcl`. В начале скрипта заданы три параметра:

- `input_gds` — путь к проверяемому файлу: `../gds/seven_segment_seconds.gds`;
- `top_cell` — имя верхнего блока внутри GDS: `seven_segment_seconds`;
- `report_file` — имя выходного отчета: `seven_segment_seconds_drc.txt`.

Пути отсчитываются от рабочей папки `work/drc`. Для текущего проекта значения уже заполнены.

Файл `scr/drc/sky130A.magicrc` подключает правила из `skywater-pdk/libs.tech/magic/sky130A.tech`. В самом скрипте выбирается полный стиль геометрической проверки `drc(full)`.

5. В активированной среде LibreLane/OpenLane запустите **новый сеанс Magic**:

```bash
magic -dnull -noconsole -rcfile ../../scr/drc/sky130A.magicrc ../../scr/drc/drc.tcl > drc.log 2>&1
```

После завершения просмотрите журнал и отчет:

```bash
cat drc.log
cat seven_segment_seconds_drc.txt
```

## Что делает скрипт

Скрипт читает экспортированный GDS, выбирает указанный верхний блок и создает временную плоскую копию в памяти. Это позволяет проверить геометрию всей иерархии, включая стандартные ячейки и взаимодействия между ними. Затем скрипт запускает DRC, дожидается завершения проверки и выписывает отчет. Исходный GDS не изменяется, временная копия не сохраняется.

Для каждой группы нарушений в отчете приводятся текст правила и прямоугольники маркеров в формате `llx lly urx ury`. Координаты указаны в микрометрах. Число маркеров не обязательно совпадает с количеством независимых физических дефектов.

В конце отчета находится итоговый статус:

- `PASS` — нарушения выбранного набора правил не обнаружены;
- `FAIL` — обнаружены нарушения, ниже описаний правил приведены их координаты;
- `ERROR` — ошибка входных данных или выполнения. Если отчет не удалось создать, причина будет в `drc.log`.

Первоначальная строка `Status: RUNNING` отмечает начало запуска. Если итогового статуса нет, проверка не завершена; такой отчет нельзя считать успешным.

Код завершения процесса: `0` — PASS, `1` — FAIL, `2` — ошибка выполнения скрипта. Ошибка запуска самого Magic также может завершить процесс с ненулевым кодом без отчета.

Проверки антенн и плотности в этот шаг не входят. `PASS` относится к геометрическим правилам Magic, подключенным в данном запуске.

## Просмотр маркеров в KLayout

Графический интерфейс Magic для просмотра результатов не требуется. KLayout может отобразить маркеры из отчета Magic поверх исходного GDS.

Из папки `work/drc` преобразуйте завершенный текстовый отчет в базу маркеров KLayout:

```bash
python3 ../../scr/drc/magic_to_klayout.py seven_segment_seconds_drc.txt seven_segment_seconds_drc.lyrdb
klayout ../gds/seven_segment_seconds.gds
```

В KLayout откройте Tools → Marker Browser (в некоторых версиях пункт находится в меню Verification). Нажмите Open и выберите `seven_segment_seconds_drc.lyrdb` из папки `work/drc`.

Выберите категорию правила и маркер в списке. Маркер будет подсвечен на топологии. Режим приближения к выбранному маркеру настраивается кнопкой Configure в Marker Browser. Координаты маркеров заданы в микрометрах относительно верхнего блока `seven_segment_seconds`, поэтому исходную иерархию GDS разворачивать в плоскую структуру не требуется.

Скрипт преобразования использует стандартную библиотеку Python и не запускает новую DRC-проверку. Отчеты с незавершенным запуском или статусом ERROR преобразованы не будут. После изменения GDS необходимо заново выполнить DRC и преобразовать новый отчет.
