# Проверка топологии DRC

## Цель работы

На этом этапе мы познакомимся с проверкой топологии на соответствие технологическим правилам (DRC, англ. Design Rule Check). Проверка позволяет обнаружить такие нарушения, как недостаточная ширина дорожки, слишком малое расстояние между полигонами или недостаточная площадь участка металлизации.

Мы будем проверять GDS файл, полученный на предыдущем этапе работы. Проверка выполняется в отдельном сеансе Magic, а ее результаты будут просмотрены в KLayout. Таким образом, входными данными этапа являются финальная топология блока и правила используемой технологии, а выходными — отчет и маркеры нарушений.

## Подготовка GDS

1. Выполните раздел [«Генерация GDS»](gds.md). Убедитесь, что в папке `work/gds` появился файл `seven_segment_seconds.gds`. Завершите сеанс Magic, в котором выполнялась генерация, командой:

```tcl
quit -noprompt
```

Дальнейшие команды терминала выполняются в активированном окружении OpenLane/LibreLane.

2. Из папки `work/gds` запустите KLayout и откройте полученный файл:

```bash
klayout seven_segment_seconds.gds
```

Просмотрите топологию блока. В дереве Cells выберите верхнюю ячейку `seven_segment_seconds`. Обратите внимание, что GDS содержит как межсоединения блока, так и полную геометрию используемых стандартных ячеек. По завершении просмотра закройте KLayout.

## Знакомство со скриптом проверки

3. В терминале перейдите в папку `work/drc` с помощью следующей команды (данная команда также создаст нужную папку, если она отсутствует):

```bash
mkdir -p ../drc && cd ../drc
```

Команда выполняется из папки `work/gds`. В новую рабочую папку будут выписываться результаты проверки.

4. Откройте файл `scr/drc/drc.tcl` в текстовом редакторе. В начале скрипта заданы параметры входных данных и выходного отчета:

```tcl
if {![info exists input_gds]} {set input_gds ../gds/seven_segment_seconds.gds}
if {![info exists top_cell]} {set top_cell seven_segment_seconds}
if {![info exists report_file]} {set report_file seven_segment_seconds_drc.txt}
```

Переменная `input_gds` задает путь к проверяемому GDS, `top_cell` — имя верхней ячейки внутри этого файла, а `report_file` — имя отчета. Для рассматриваемого проекта значения уже заполнены. Пути отсчитываются от рабочей папки `work/drc`.

Правила проверки подключаются с помощью отдельного файла `scr/drc/sky130A.magicrc`. Он загружает технологический файл `skywater-pdk/libs.tech/magic/sky130A.tech`, содержащий правила SKY130 для Magic.

Основные этапы скрипта:

- Загрузка GDS с помощью команды `gds read` и выбор верхней ячейки с помощью `load`;
- Создание временной плоской копии топологии с помощью `flatten`. Это позволяет проверить геометрию стандартных ячеек и их взаимодействие с другими элементами блока;
- Выбор стиля проверки `drc(full)`, запуск DRC и ожидание завершения;
- Получение описаний нарушенных правил и координат маркеров, запись отчета.

Непосредственно проверка запускается следующим блоком команд:

```tcl
drc euclidean on
drc style drc(full)
drc on
drc check
drc catchup
set all_errors [drc listall why]
```

Команда `drc catchup` дожидается завершения проверки. Команда `drc listall why` возвращает описания нарушений и прямоугольники, отмечающие их положение на топологии.

Исходный GDS в процессе проверки не изменяется. Временная плоская копия существует только в памяти Magic и не сохраняется.

## Запуск проверки в Magic

5. Из папки `work/drc` выполните команду:

```bash
magic -dnull -noconsole -rcfile ../../scr/drc/sky130A.magicrc ../../scr/drc/drc.tcl > drc.log 2>&1
```

Данная команда запускает новый сеанс Magic, подключает технологический файл и выполняет скрипт проверки. Ключ `-dnull` отключает графическое окно, а `-noconsole` — отдельное окно консоли. Вывод программы сохраняется в `drc.log`. После завершения скрипта Magic автоматически закроется, и в терминале снова появится приглашение для ввода команд.

6. Откройте журнал `drc.log` и отчет `seven_segment_seconds_drc.txt`:

```bash
cat drc.log
cat seven_segment_seconds_drc.txt
```

В конце отчета приведены количество групп правил (`Rule groups`), число маркеров (`DRC markers`) и итоговый статус:

- `PASS` — нарушения выбранного набора правил не обнаружены;
- `FAIL` — проверка завершена, обнаружены нарушения;
- `ERROR` — проверка не выполнена из-за ошибки входных данных или выполнения.

В начале отчета находится строка `Status: RUNNING`, отмечающая начало запуска. Результат определяется последней строкой статуса. Если итогового статуса нет, проверка не завершена. Если отчет не появился, обратитесь к журналу `drc.log`.

Код завершения процесса равен 0 при отсутствии нарушений, 1 при наличии нарушений и 2 при ошибке выполнения скрипта. Поэтому ненулевой код при статусе `FAIL` не означает, что скрипт не сработал.

## Анализ отчета

7. При наличии нарушений найдите в отчете описание правила и расположенные под ним строки координат. Например:

```text
Metal3 minimum area < 9600 (met3.6)
72.285 38.230 72.615 38.245
```

Это пример нарушения минимальной площади участка металла на третьем слое металлизации. Обозначение `met3.6` позволяет идентифицировать правило. Числовое значение в тексте правила выводится Magic; оно не является площадью в квадратных микрометрах.

Каждая строка координат задает прямоугольник в формате `llx lly urx ury`: координаты нижнего левого и верхнего правого угла соответственно. В нашем отчете координаты приведены в микрометрах относительно верхнего блока.

Одно физическое нарушение может быть представлено несколькими прямоугольниками. Поэтому число маркеров не обязательно совпадает с количеством независимых дефектов. Результаты вашего запуска могут отличаться от приведенного примера.

Если получен статус `PASS`, зафиксируйте отсутствие маркеров и перейдите к преобразованию отчета.

## Просмотр маркеров в KLayout

8. В той же папке `work/drc` выполните команду:

```bash
python3 ../../scr/drc/magic_to_klayout.py seven_segment_seconds_drc.txt seven_segment_seconds_drc.lyrdb
```

Скрипт создаст базу маркеров KLayout в формате `.lyrdb`. При этом сохраняются описания правил, имя верхнего блока и координаты прямоугольников. Новая DRC-проверка не запускается — преобразуются результаты Magic. Для запуска скрипта достаточно Python 3.9 или новее, дополнительные пакеты Python не требуются.

Отчеты с незавершенной проверкой или статусом `ERROR` не преобразуются. При статусе `PASS` будет создана база без маркеров.

9. Запустите KLayout и откройте проверенный GDS:

```bash
klayout ../gds/seven_segment_seconds.gds
```

В верхнем меню выберите Tools → Marker Browser (в некоторых версиях пункт находится в меню Verification). В окне Marker Browser нажмите Open или воспользуйтесь меню File → Open и выберите файл `seven_segment_seconds_drc.lyrdb` из папки `work/drc`.

В поле «… on layout» должен быть выбран `seven_segment_seconds.gds`. В дереве Cells основного окна KLayout должна быть открыта верхняя ячейка `seven_segment_seconds`.

10. В левой части Marker Browser раскройте список By Category и выберите категорию нарушения. В правой части появятся маркеры этой категории. Нажмите на конкретную строку в списке Markers и просмотрите информацию о ней в поле Info.

Настройки подсветки и приближения к выбранному маркеру доступны по кнопке Configure. Отодвиньте окно Marker Browser в сторону, чтобы оно не закрывало интересующий участок топологии. Размеры маркеров могут составлять доли микрометра, поэтому на общем виде блока они практически не видны.

Для приведенного выше нарушения `met3.6` просмотрите GDS-слой `70/20`, соответствующий металлизации `met3` в SKY130. Соответствие слоев приведено в файле `skywater-pdk/lef2gds.map`.

Если получен статус `PASS`, убедитесь, что Marker Browser показывает пустую базу.

## Результаты работы

11. Зафиксируйте в отчете по лабораторной работе:

- Имя проверенного GDS и верхней ячейки;
- Используемые технологический файл и стиль проверки;
- Итоговый статус, число групп правил и число маркеров;
- При наличии нарушений — описание одного правила, координаты соответствующего маркера и изображение участка топологии с его подсветкой в KLayout.

Сохраните файлы `drc.log`, `seven_segment_seconds_drc.txt` и `seven_segment_seconds_drc.lyrdb` в папке `work/drc`. После изменения GDS необходимо повторить проверку и заново преобразовать отчет, чтобы маркеры соответствовали новой топологии.

**Заключение**

На этом мы познакомились с отдельным этапом проверки готового GDS по технологическим правилам и просмотром результатов в графическом редакторе.

В данной работе используется геометрическая проверка Magic. Проверки антенн и плотности выполняются отдельно и в этот шаг не входят. Статус `PASS` относится только к правилам, включенным в данном запуске.
